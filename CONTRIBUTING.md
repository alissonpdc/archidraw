# Contributing to ArchiDraw

Thanks for your interest in contributing! This document covers the project setup and conventions.

## Setup

Requirements: **Node.js 22+** and **npm** (CI runs on Node 22).

```bash
git clone <repo-url> && cd archidraw
npm install
npx playwright install chromium   # required for E2E tests
npm run dev
```

## Commands

| Command | Description |
|---|---|
| `npm run dev` | Dev server (Vite) |
| `npm run build` | Typecheck + production build |
| `npm run lint` | Linter (oxlint) |
| `npm run test:e2e` | Playwright tests (real build + preview) |
| `npm run test:e2e:ui` | Interactive Playwright UI |

## Architecture

- **`src/core/`** — pure, no React: document model (`types.ts`), camera (`utils.ts`), hit-testing, undo/redo history (`history.ts`), Canvas 2D renderer (`renderer.ts`), and state machine (`editor.ts`, `Editor` class).
- **`src/ui/`** — thin React shell for presentation. State flows via `useSyncExternalStore(editor.subscribe, editor.getSnapshot)`.

Critical rules:

1. State/interaction lives in `src/core/`; `src/ui/` is presentation only.
2. `Editor.getSnapshot()` must return a **stable** reference (cache invalidated only on `emit()`). Creating a new object on every call causes an infinite render loop.
3. Before implementing UI/interactions, check `.agents/knowledge/*.md` — lessons from recurring bugs with mandatory rules.

## Contribution flow

1. Create a branch with a conventional prefix from `main` (`feat/...`, `fix/...`, `chore/...`, `refactor/...`, `perf/...`, `test/...`, `docs/...`, `ci/...`, `style/...`, `build/...`). Branches outside these prefixes won't trigger CI.
2. Push the branch — CI (`.github/workflows/ci.yml`) runs **lint + typecheck + security audit + E2E + build** in parallel jobs; the auto-PR step is gated on a fully green pipeline.
3. Once the pipeline is green, a **PR to `main` is opened automatically** (subsequent pushes to the same branch update the existing PR).
4. Review/request review and merge — the merge triggers an automatic release (GitHub Release + Docker Hub).

### Release Pipeline

Triggered when a **PR to `main` is closed and merged** (`.github/workflows/release.yml`):

1. Full validation: **lint + typecheck + build + E2E**.
2. **Automatic semantic versioning** from conventional commits since the last tag (`.github/workflows/release.yml`):
   - any commit with a breaking marker (`!:` or `BREAKING CHANGE`) → **major**
   - else any `feat` commit → **minor**
   - else → **patch** (covers `fix`, `perf`, `chore`, `docs`, etc.)
3. **GitHub Release** with notes generated by `.github/scripts/generate_release_notes.py` (via OpenRouter, with fallback).
4. **Docker Hub**: image published with tags `X.Y.Z`, `X.Y`, and `latest`. Requires the secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` (see README, "Docker Hub Authentication" section).

This is why the commit message matters: it defines the version bump.

### Before pushing

1. Implement with tests covering the new behavior (E2E specs in `e2e/specs/`).
2. Run the full GATE locally (required — see below).

### Definition of Done (required)

A task is only **done** when both conditions are met:

1. **Test GATE:** `npm run lint && npm run build && npm run test:e2e` passed without errors (mirrors the CI `validate` job in `release.yml`, which additionally runs `tsc -b`). Without a green run, do not report it as complete.
2. **Local commit** (or PR) with a message following **Conventional Commits**.

## Conventions

### Commits

**Conventional Commits** format, in pt-BR or English (be consistent):

```
feat: add ctrl+scroll zoom
fix: fix clipped tooltip in toolbar
refactor: extract hit-testing to utils
test: cover undo/redo in multi-selection
docs: update README with Docker instructions
```

### Code style

- No comments in code unless requested/strictly necessary.
- Follow existing conventions from neighboring files (imports, typing, naming).
- No secrets or keys in the repository.

### E2E Tests (Playwright)

- Use the `test` fixture from `e2e/fixtures.ts` — **never** the one from `@playwright/test` directly. Every page is monitored: any `console.error/warning` or `pageerror` fails the test.
- Use the `open(page)` helper to navigate and wait for hydration (`__appReady__`).
- Internal state: `window.__editor__` exposed in dev/test builds; read via the `editorState()` fixture.

### Recurring bugs

When fixing a bug that warrants a general rule (a problem that has happened more than once), add an entry in `.agents/knowledge/` and reference it in `AGENTS.md`.

## Reporting bugs

Open an issue with: steps to reproduce, expected vs. observed behavior, and environment (OS, browser, version). If possible, include an exported JSON of the diagram (remove sensitive data).
